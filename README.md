# Sports Predictor

A local, multi-sport prediction and market-tracking system in the Walters
tradition: model probabilities, market comparison, and disciplined
evaluation — running entirely on one machine (Python + SQLite, CLI-first,
with a FastAPI browser UI).

**Live sports:** MLB (production), Premier League soccer (production),
NFL (gate-passed, in dress rehearsal), plus data/tracking coverage for
the EFL Cup, Champions League, Europa League, and the English pyramid
(Championship, League One, League Two).

> Prediction tool, not betting advice. Outputs are model probabilities
> and their relationship to market prices.

---

## How the system thinks

The codebase is organized around a few hard rules, learned live and
enforced by machinery rather than memory:

- **Gates before promotion.** Every retrained model candidate faces a
  frozen holdout gate (`improve`, `soccer-refresh`); candidates that
  don't clear it are rejected regardless of how promising they look.
  Guards include log-loss thresholds, rating-drift limits, and an
  Elo spread-compression check.
- **Pre-committed reads.** Calibration questions get their decision
  rules written *before* the data arrives (sample size, threshold,
  verdict logic), then the ledger accrues until the read is due.
- **Tracking before shipping.** New sports and features run internally
  (rehearsal flags, market-only exports) until they earn live status
  through backtests and dress rehearsals.
- **Honest gaps.** Missing inputs are labeled (`book_odds: 0`,
  `kalshi: absent`), never silently filled. Refuse-safe matchers prefer
  a coverage gap to a wrong match.
- **Layer separation.** This system predicts and tracks; a downstream
  consumer makes betting decisions. Files state what they contain
  (`contains_predictions`, `rehearsal` flags).

## Architecture

```
CLI (cli.py) ─────────────── daily chains per sport
  │
  ├─ src/adapters/       API-Football, MLB Stats API, API-Baseball,
  │                      API-American-Football, Kalshi — normalized
  ├─ src/ingestion/      sync services, market matchers, injury feeds
  ├─ src/models/         Elo (+ per-team season regression), Poisson,
  │                      NegBin/Pythagorean, factors
  ├─ src/walters/        training + gates, prediction, evaluation,
  │                      exports, NFL backtest/predict/grade, card
  ├─ src/web/            FastAPI + Jinja2 + HTMX local UI
  └─ data/sports.db      SQLite (gitignored — local only)
```

## Quickstart

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt        # or: sqlalchemy requests python-dotenv click rich fastapi uvicorn jinja2
cp .env.example .env                   # add your api-sports key(s)
python cli.py sync-competitions --sport soccer
python cli.py sync-teams --competition PL --season "2026/27"
python cli.py sync-matches --competition PL --season "2026/27"
```

Season string formats: soccer uses `"2026/27"`; MLB and NFL use `2026`.

## Daily operation (the chains)

**MLB (daily):** `sync-matches → sync-bullpen → sync-pitchers →
sync-pitcher-stats → sync-odds → sync-kalshi → predict → sync-umpires →
capture-weather → export-predictions`; mornings run `evaluate → improve →
sync-appearances → export-results`.

**Soccer (weekly rhythm):** pre-matchday chain (`sync-matches →
sync-odds → sync-injuries → sync-kalshi-soccer → predict →
export-predictions`), morning-after grading, and a gated
`soccer-refresh` after each matchweek. See `docs/pl_weekly_routine.md`.

**NFL (weekly):** `sync-odds-nfl` / `sync-kalshi-nfl` through the week
as lines post; `sync-matches` + `nfl-grade` after game days;
`predict-nfl → export-nfl-predictions` (rehearsal-flagged until live).

**Cups (EFL/CL):** data syncs and market-only `export-fixtures` files;
model predictions are withheld until the cup path passes its
pre-committed acceptance test.

## CLI reference

The CLI is the primary interface (the web UI covers MLB and soccer views
only — NFL and cups are CLI-operated). The full command catalog, with
options, per-sport chains, required API endpoints, and component
requirements: **[`docs/CLI.md`](docs/CLI.md)**.

## Documentation

- `RESULTS.md` — rolling 30-day record per sport, regenerated by
  `python cli.py results-tally` (part of the morning rhythm).
- `BACKLOG.md` — the living operational record: findings, incidents,
  pre-committed tests, and their verdicts, in reverse-chronological
  detail. The project's institutional memory.
- `CHANGELOG.md` — human-readable summary of what shipped, by date.
  Every drop adds an entry going forward.
- `docs/` — per-sport runbooks and routine documentation.

## Repo workflow

Code changes are authored in working sessions, delivered as a tarball,
extracted over this working tree, then committed and pushed — so `main`
always reflects the running system. The SQLite DB and `.env` never
enter the repo; the DB is backed up separately (`sqlite3 data/sports.db
".backup ..."`).
