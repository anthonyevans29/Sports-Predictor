## 2026-11-11 (#925: 921-sync-hold — SP_SYNC_HOLD: a per-competition sync hold the step itself honors (ARCHITECT 2026-11-10, addendum 332 item 3; 333 item 3(iii)).)
- **Ruling (verbatim, addendum 332 item 3):** "THE DURABLE ANSWER is a per-competition sync hold the step itself honors: SP_SYNC_HOLD, a list of competition codes read by sync-teams and sync-matches, which print "HELD <code> (SP_SYNC_HOLD)" and exit 0 for a listed code, every chain and timer unchanged, the window and fullseason plans unchanged; a receipt line counts the held steps." And 333 item 3(iii): "SP_SYNC_HOLD (#921) honors the same path: its design covers intl-sync, or says in its body why not."
- **Built:**
  - `src/ingestion/sync_hold.py`: the setting and the line. Read on every check from the process environment, host.env (`SP_HOST_ENV`) and the checkout's .env; a code named in any of them is held (a run by hand and the long-running admin UI see it with no restart). Codes are separated by commas or blanks, any case.
  - `cli.py`: `sync-teams`, `sync-matches` (every source; the MLB api-sports fallback and the tennis path included; `--match-ids` and `--seasons` included) and `refresh-by-id` check the setting first. A held code prints `HELD <code> (SP_SYNC_HOLD)`, builds no adapter, makes no provider call, writes nothing and exits 0.
  - `intl-sync` (src/ingestion/intl_history.py): a held code of the plan is not written (competition, teams, memberships, matches, neutral rows); the run prints one HELD line per held code; its coverage row reads `skipped HELD`. The fetch and the team filter are unchanged.
  - The admin UI's two sync jobs return the HELD line for a held code.
  - `sp_run`: the chain receipt's `sync_held` {n, steps} and `sync_hold` (the setting as parsed, by place); the summary line's ` · held steps (SP_SYNC_HOLD) N: …` and ` · SP_SYNC_HOLD <codes>`; a held competition's receipt line; each freshen run's `sync_held`; and the receipts table's key line (`sp_receipts`).
  - `closing.py`: a held step in a closing run is recorded (`held` on the step, `sync_held` on the run). **THE HELD CLOSING READ (ARCHITECT 2026-11-11 09:35 ET, addendum 336 item 1, verbatim):** "the CLOSING RUN, which already records the held step, treats a held A1 schedule read exactly as it treats an A1 read that was not answered today — the same path, the same receipt fields, the same notice, nothing new invented — with the cause named `schedule_held (SP_SYNC_HOLD <code>)`. It does not go on with the stored schedule to an export, a page or a push for that family." A1 is per family today (each family's closing covers one competition; a read that did not answer fails the whole run), so a held read fails the family's run at that step: `failed` = `step i (schedule read: schedule_held (SP_SYNC_HOLD <code>), A1)`, the failed-run notice and the attempt as for an unanswered read, nothing exported, paged or pushed. The slate stage runs the same reads: a held slate read is recorded on the slate receipt (`held`, `sync_held`) and the slate goes on (336 item 1 names the closing run; the slate is put to the architect).
  - The hosting runbook's hold procedure gains the setting as the first move; docs/CLI.md; both env examples.
