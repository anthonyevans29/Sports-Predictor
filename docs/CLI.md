# CLI Reference

The CLI is the primary interface — the browser UI currently covers MLB and
soccer views only, so NFL and the cup competitions are operated entirely
from here. Every command: `python cli.py <command> [options]` from the
repo root with the venv active.

Conventions: soccer seasons are `"2026/27"`; MLB and NFL seasons are
`2026`. Competition codes: `PL`, `ELC`, `EL1`, `EL2`, `EFL` (League Cup),
`FAC`, `CL`, `UEL`, `CS`, `MLB`, `NFL`. Dates are `YYYY-MM-DD`.

## MLB daily operation

Pre-slate chain, in order: `sync-matches --competition MLB --date-from <today> --date-to <today>` → `sync-bullpen-stats` →
`sync-pitchers` → `sync-pitcher-stats` → `sync-odds` → `sync-kalshi` →
`predict` → `sync-umpires --today` → `capture-weather` → `export-predictions`.

Morning chain (laptop), split into **two phases by network mode**
(architect 2026-10-01). The two modes conflict, so never run them together.

1. **Phase 1, VPN on (the statsapi steps).** Open with the backup line,
   then run the morning grading: `sync-matches` → `evaluate` → `improve` →
   `sync-appearances --recent` → `sync-umpires --recent` →
   `export-results`. The statsapi calls are `sync-matches`,
   `sync-appearances` and `sync-umpires`. The rest is local, so it runs
   in this phase too. Then, after the MLB sync and never inside the watch,
   the retire step (ARCHITECT 2026-10-20, addendum 146 item 3(a), #568:
   "explicit, dry run first, in the morning block after the MLB sync"):
   the dry run `python cli.py retire-orphans --competition MLB --season 2026`
   (at most one statsapi call), pasted with the morning receipts; then, for
   the rows it planned `retire`, a fresh `.backup` and `python cli.py
   retire-orphans --competition MLB --season 2026 --apply --backup PATH
   --match-ids <the ids the dry run planned>`. Nothing planned, nothing to
   apply. Then the college kickoffs (ARCHITECT 2026-10-09,
   addendum 21 item 1: "at least once a day on the host and in the
   laptop's morning chain"): first the listing reads, `sync-matches
   --competition NCAA --season 2026 --date-from D --date-to D` for each of
   D = today .. today+7, one day per call; then `refresh-by-id --competition
   NCAA --days 7`. ARCHITECT 2026-10-09, addendum 30 item 4:
   "The laptop's morning chain reads NCAA by date for today to today+7, one day per call, and then runs refresh-by-id, as ncaa-schedule does on the host. After a re-key the listing reads carry the new ids and the refresh confirms them; in the other order every re-keyed game prints as not found."
   These are api-sports calls, not statsapi, like the pre-slate chain's
   `sync-odds`. Paste the `sync-matches` lines and the `REFRESH-BY-ID` lines
   with the morning receipts.
2. **Switch.** QUIT the VPN client; disconnecting is not enough, because
   it can keep its tunnel or DNS hooks (hosting-h1 field amendment
   2026-09-28). Then bring Tailscale up.
3. **Phase 2, Tailscale on (the host steps).** Run
   `python deploy/hosting/pull_exports.py`, then
   `python deploy/hosting/compare_exports.py exports exports/host`. The
   compare defaults to `--since 3`, so settled exhibits stop re-printing.
   Then paste the host receipts table
   (`ssh sp@sp-vps-1 'sudo -u sp venv/bin/python deploy/hosting/sp_receipts.py --since 24h'`).

The series is the rows of the row's season and stage with its two teams either way round, of every status; `games_in_series` is the one value its rows carry, needed = (gis + 1) // 2; wins per side over its FINISHED games. DECIDED when a side has `needed` wins over the k FINISHED games and the series ended before this row's game: its own game number after the clinch's (the clinch's stored game number, which must equal k; with none stored the receipt says `after k FINISHED games` (with none stored, k stands in for it, and a FINISHED row storing a number of k or more is no receipt: a FINISHED game of the series is not stored; with no number stored on any FINISHED row, a FINISHED game not stored cannot be seen)), or, with its own number null, the clinch's start before its own (`game number: null (own); read by start`; at the same start, NOT DECIDED). NO RECEIPT for `games_in_series` null on every row or disagreeing, a `games_in_series` under 1 or even (a best-of-N is odd: an even N lets both sides reach `needed`, a tie), the series columns not migrated (`migrate_match_series_fields.py`), a LIVE game of the series, a FINISHED game without a decided score, two FINISHED rows of one gamePk or one game number, more FINISHED games than `games_in_series`, a side past `needed`, two FINISHED games sharing the latest start, two FINISHED games on one ET day (one game stored twice under two ids; #631 review), a clinch (the latest FINISHED game) the other side won, or a clinch whose stored game number is not k (`a FINISHED game of the series is not stored (clinch is game N, k FINISHED)`, or more FINISHED rows than its number). Two more guards, a FINISHED game or the row with no start, cannot fire on a current-schema DB (`matches.utc_date` is NOT NULL). `series_description` is printed, never a gate. Each series row is printed with its gamePk, game number, start, status, `status_raw` and score. The plan: `retire` only on ABSENT and DECIDED; every other row stays SCHEDULED, labelled `listed`, `not decided`, `no receipt 1` or `no receipt 2`, both receipts printed. **`--apply`** needs `--backup PATH` (a `.backup` taken just before: the `dedupe-matches` check, its matches count equal to the live DB's, so the morning's opening backup is behind once the sync has created a row) and `--match-ids` naming the rows the dry run planned `retire` (as `merge-teams` names its pairs; `--match-ids` without `--apply` is refused). Refusals, each exit 2, no provider call, nothing written: a competition other than MLB; `SP_SKIP_FAMILIES` naming MLB (the host's api-sports fallback); a `--season` that is not digits; no database file at the configured path (law 5: never created, the migrations' shared guard, #524); `--apply` without `--backup` or `--match-ids`; the backup check; a DB behind the code.
