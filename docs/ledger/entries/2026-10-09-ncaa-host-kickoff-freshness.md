- **Cause, from the code (the host runs v1.3.0):**

  - **ncaa-market at v1.3.0:** single-day syncs of `{yesterday}` and `{today}` (v1.3.0 `deploy/hosting/chains.py:172-174`), timer Thu/Fri 16:00 and Sat 13:00 UTC. Main added `{tomorrow}` and Tue/Wed (#320, not in v1.3.0). A game two days out is never fetched. A game inside the window is fetched only on a run whose yesterday/today/tomorrow includes its UTC date. The Thu 10-08 16:00Z run synced 10-07 and 10-08 only, which is why that day's host fixtures file had 38 placeholders.
  - **The window service (hourly):** a game two days out is outside its query (`m.utc_date >= now AND < now+24h`, `deploy/hosting/sp_run.py:94`), so the window plans no step for it. A game inside the window gets a single-day sync of each UTC date in {now, now+24h} (`sp_run.py:103`, `:118-120`). So from 06:05Z on 10-09 every run called NCAA `date=2026-10-10`.
  - **The window question is not settled by the code.** That call overwrites the kickoff of every stored id the provider lists. So those 30 ids were not listed with an announced time on the window's `date=2026-10-10` responses. Either (a) the date-filtered listing still carried 04:00Z for them, or (b) the announced time came under a new provider id. In case (b) a new id whose kickoff is more than `REKEY_WINDOW_H = 12` hours from the stored 04:00Z (23:30Z is 19.5h away) is not re-keyed onto the placeholder row (`service.py:72`, `:490-491`). The step receipts settle it: the window's NCAA `sync-matches` lines in `receipts.jsonl` between 06:05Z and 11:05Z on 10-09 show `created`/`updated`, and `scripts/kickoff_receipt.py --find "Alabama" --date 2026-10-10` prints the stored row and the provider's raw date block for its id. - **How the provider marks an unannounced time:** the only repo evidence is the 2026-10-05 architect ruling, encoded in `scripts/ncaa_rekey_receipt.py:234-236`: "The provider's TBD kickoff: 04:00:00Z (midnight US Eastern)".   - **Built:**
    - New command `refresh-by-id --competition NCAA --days 7` (`cli.py`, logic in `src/ingestion/refresh_by_id.py`). It takes every stored SCHEDULED row of the competition with a kickoff on the UTC dates today .. today+7, the same dates as the chain's listing reads. Each row gets one `GET /games?id=` through the adapter's existing `get_game` (`src/adapters/api_american_football.py`).
    - It applies the kickoff (`utc_date`), the status (the adapter's `_STATUS` map: unknown stays SCHEDULED, law 4) and the score (only when given).
    - The rate-limit rule is sync-odds-football's, on the same constants and seams. Calls are paced at `SP_ODDS_FOOTBALL_RPM` (default 280/min). A `RateLimited` answer (a second 429 inside the adapter) is deferred, then retried after Retry-After (else 60s) for up to `ODDS_RETRY_ROUNDS` = 2 rounds. A game still limited after those rounds is listed and untouched, and the step exits 1.
    - Never guessed: NOT FOUND (an empty answer) is counted, listed and untouched. An answer for different teams is REFUSED and untouched. A lookup error is UNRESOLVED (never read as absent), listed, untouched, and exits 1. A row with no provider id is listed.
    - The receipt is printed (counts line, then each kickoff moved with both times, status and score changes, and each not found / refused / unresolved game). It is also appended to the receipts log (`sp_common.append_receipt`, kind `refresh_by_id`), and the last line is `REFRESH-BY-ID-RECEIPT {counts}`.
