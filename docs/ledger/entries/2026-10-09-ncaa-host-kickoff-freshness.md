**2026-10-09 — FINDING + FIX (ARCHITECT addendum 19 item 3, track H, host only): the host's college kickoff times were stale. A daily forward-week NCAA sync now keeps them fresh.**
- **Ruling (verbatim):** "NEW FINDING, host only: the host's college kickoff times are stale. At 11:06Z today the host's window card (0023368) showed 30 of Saturday's games at 2026-10-10T04:00Z, the provider's placeholder, inside its 24-hour window, with no books and no Kalshi on any of them. The laptop's file of 2026-10-08 21:56Z has announced kickoffs for 27 of the 30 (Georgia at Alabama 23:30Z), and its file of 2026-10-06 already had 91 of Saturday's 95. Yesterday's 16:00Z host fixtures file had 38 placeholders against the laptop's 4. It is why I did not count 2026-10-08 as a clean compare day: by the Exhibit 1 precedent a chain gap is not an explained class.
Open an Issue (track H, finding, ncaa). Cause first, from the code and the provider's responses (law 1): the host's ncaa-market chain syncs yesterday and today only, and the hourly window service had these games inside its window for seven hours without moving them. Say what each of the two does for an NCAA game two days out and for one inside the window, and how the provider marks an unannounced time, if it does.
Then the fix, its own small PR, before the next tag: 'On the host, the stored kickoff of every NCAA game in the next seven days is at most one day old.' One test that fails on today's chain."
- **Cause, from the code (the host runs v1.3.0):**
  - Only `sync-matches` writes a stored kickoff. For a provider id already stored, `_apply_match_updates` overwrites `utc_date` unconditionally (`src/ingestion/service.py:429`). The american-football adapter sends `date` only when from == to (`src/adapters/api_american_football.py:208-209`).
  - **ncaa-market at v1.3.0:** single-day syncs of `{yesterday}` and `{today}` (v1.3.0 `deploy/hosting/chains.py:172-174`), timer Thu/Fri 16:00 and Sat 13:00 UTC. Main added `{tomorrow}` and Tue/Wed (#320, not in v1.3.0). A game two days out is never fetched. A game inside the window is fetched only on a run whose yesterday/today/tomorrow includes its UTC date. The Thu 10-08 16:00Z run synced 10-07 and 10-08 only, which is why that day's host fixtures file had 38 placeholders.
  - **The window service (hourly):** a game two days out is outside its query (`m.utc_date >= now AND < now+24h`, `deploy/hosting/sp_run.py:94`), so the window plans no step for it. A game inside the window gets a single-day sync of each UTC date in {now, now+24h} (`sp_run.py:103`, `:118-120`). So from 06:05Z on 10-09 every run called NCAA `date=2026-10-10`.
  - **The window question is not settled by the code.** That call overwrites the kickoff of every stored id the provider lists. So those 30 ids were not listed with an announced time on the window's `date=2026-10-10` responses. Either (a) the date-filtered listing still carried 04:00Z for them, or (b) the announced time came under a new provider id. In case (b) a new id whose kickoff is more than `REKEY_WINDOW_H = 12` hours from the stored 04:00Z (23:30Z is 19.5h away) is not re-keyed onto the placeholder row (`service.py:72`, `:490-491`). It is created as a second row, and the placeholder row is left untouched. The step receipts settle it: the window's NCAA `sync-matches` lines in `receipts.jsonl` between 06:05Z and 11:05Z on 10-09 show `created`/`updated`, and `scripts/kickoff_receipt.py --find "Alabama" --date 2026-10-10` prints the stored row and the provider's raw date block for its id. Neither is run here (no host, no key).
- **How the provider marks an unannounced time:** the only repo evidence is the 2026-10-05 architect ruling, encoded in `scripts/ncaa_rekey_receipt.py:234-236`: "The provider's TBD kickoff: 04:00:00Z (midnight US Eastern)". The adapter reads only `date.timestamp` (`api_american_football.py:233-236`) and `status.short` (`:243-245`, unknown codes become SCHEDULED, no TBD code in `_STATUS`). No code reads `date.time`, and the repo holds no recorded NCAA `/games` payload. So whether the provider also flags the time (for example a `time` of "TBD", or a status code) cannot be determined from repo evidence.
- **Fix:**
  - New host chain `ncaa-schedule`: single-day NCAA `sync-matches` for today..today+7, sync only.
  - New timer `sp-ncaa-schedule.timer`, every day at 10:35 and 22:35 UTC. ncaa-market runs Tue-Sat, and one failed run still leaves the kickoff under a day old.
  - `{today_plus1..7}` date vars.
  - ncaa-market, the window and the adapter are unchanged.
- **Limit (law 4):** if the cause is (b), a sync refreshes the new id's row and leaves a 04:00Z twin. That is the existing `dedupe-matches --orphans` class. The invariant then holds for every live provider id, not for the orphan. The receipts above decide whether this needs its own ruling.
