- **The finding (#798, from Codex's round-1 review of #797):** `reserve()` caught only `FileExistsError` at the exclusive create, so ENOSPC, EACCES or EIO there escaped as a traceback (nothing created, so the read was not spent; only a less clear exit). After a failed write, `os.unlink` was not followed by a directory fsync while the refusal said "the read is not spent"; after a crash before the directory was flushed, the partial file could return and read as a spent run. No incident is known.
- **The fix:** any `OSError` at the create other than `FileExistsError` refuses ("could not be created (...); nothing written, nothing scored, the read is not spent"). After the cleanup the directory is fsynced in both outcomes (our unlink removed the file, or it was already gone). If that fsync fails, the refusal says the removal could not be made durable, names the file to check before the run, and ends "nothing scored", never "the read is not spent". The messages match #797's wording, so the two harnesses read the same.
